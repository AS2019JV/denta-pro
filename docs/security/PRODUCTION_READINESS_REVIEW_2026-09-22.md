PostgreSQL explicitly documents that SECURITY DEFINER uses the function owner's privileges. This is the basis of PR-01, rather than the mere presence of a definer function. [PostgreSQL function security](https://www.postgresql.org/docs/current/sql-createfunction.html). Public buckets bypass read access controls for file serving. [Supabase bucket access model](https://supabase.com/docs/guides/storage/buckets/fundamentals).

## Why the reported 436 passing assertions are insufficient

`test/security/harness/database-security-engine.cjs:283` implements authorization again in JavaScript; it checks `caller.role !== 'service_role'`, unlike PostgreSQL's function-owner execution context. `tier1-features.test.cjs:37` constructs that simulator. The migration verifier searches source text across migration files; matching a guard string does not execute it or establish the final deployed policy set.

These tests can pass while real PostgreSQL skips the guard or rejects a query. Keep useful unit tests, but label simulated checks accurately and add integration tests against the actual schema/migrations. The previous 436 assertions and build/typecheck results are report claims; they were not rerun here. `next.config.mjs` still ignores TypeScript and lint failures during builds, so build success alone is not a release gate.

## Additional hardening and operational gaps

- **Email:** require active membership before service-role recipient lookup; use exact normalized email equality instead of ILIKE pattern matching. Generate or allowlist HTTPS link destinations: HTML escaping at `app/api/send-email/route.ts:85` does not validate a URL. Replace process-local fixed-window Maps with a shared limiter/queue and enforce payload limits. Current limits are 30/IP/minute and 100/clinic/minute, not a cluster-wide guarantee.
- **RPC inventory:** review every exposed definer function, not just the named three maintenance RPCs. Live `cleanup_soft_deleted_records()` is anonymous-callable and deletes notifications older than 90 days across clinics; restrict this operational action to the scheduler/service role. Trigger-returning functions listed by an advisor are not automatically directly exploitable RPCs.
- **Storage/financial boundary:** live `receipts` is public, with public read/upload policies. This was a configuration-only observation; no receipt or bank data was read. Initial bank transfers do not justify public receipts. Keep sensitive proofs outside that bucket or secure it before use. Finance pages/payment APIs must be disabled server-side if outside the launch scope; hiding navigation is insufficient.
- **Rights evidence:** M4 grants broad INSERT/UPDATE with row-level ownership rules. Revoking DELETE alone does not make request history immutable. Protect original requester, details and timestamps; keep append-only transition events and controlled resolution actions.
- **Release operation:** add real TypeScript/lint gates, dependency/secret scanning, admin MFA, tested backup-and-restore including storage, access audit trails without unnecessary clinical payloads, alert ownership, incident response and a rollback rehearsal. These operational controls were not validated in this review.

## Ecuador LOPDP readiness

Ecuador's LOPDP is the baseline. Document the clinic/provider controller–processor roles, lawful basis by purpose, patient notices, rights handling, retention/legal holds, incident duties and vendor/hosting transfers. Brazil hosting requires a documented international-transfer assessment; location alone neither proves nor defeats compliance.

Correct the report's DPD reference: the designation provision is Article 48, not 47. Assess designation/registration and impact-assessment duties under applicable current health-data/scale rules. [SPDP guidance and consultations](https://spdp.gob.ec/consultas2026/). The official register lists a 2026 risk/impact-assessment guide; use the current version rather than relying solely on the 2025 checklist. [Registro Oficial, Supplement 254](https://www.registroficial.gob.ec/suplemento-no-254/).

Do not present a code-defined 90-day purge lock or an unsupported blanket “5–10 years” as the legal retention schedule. Have the responsible privacy/clinical adviser identify binding periods by record type, including minors, and approve deletion exceptions. Reconcile contradictory article references in the repository rules and reports. These organizational/legal requirements cannot be certified by code tests.

## Ordered next steps and release gates

1. **Containment — engineering/operations, before real patient onboarding:** resolve PR-01–04 as one coordinated security repair. Restrict the unguarded family RPC immediately through a reviewed migration; inventory patient media before a coordinated privacy migration. If real data is already present, restrict access and assess relevant access logs for possible exposure. The findings do not establish that a breach occurred.
2. **Authorization repair — backend/database:** use one active membership authority, protected profile columns, bounded RPC grants and tenant-safe object relationships. Address PR-05/06 and invitation authorization. Version all live-only functions. Give new migrations unique ordered versions; the four local M1–M4 filenames share the same 20260920 prefix while deployed versions differ, so prove fresh installation and upgrade produce equivalent schemas.
3. **Real regression gate — QA/security:** synthetic tenants A/B; owner, doctor, receptionist, removed and anonymous actors. Exercise PostgREST and Storage with end-user JWTs, including direct table/RPC requests. Assert forbidden operations fail and approved signup, invitation, removal, patient list/detail, charting, prescription and file workflows succeed. Verify actual database effects, not merely HTTP status. Include pagination and invalid related-patient references.
4. **Privacy and operations — product/DPD/operations:** finish PR-07, rights-history integrity, retention/transfer documentation, email controls, MFA and restore/incident drills. Resolve or justify each advisor notice. Set a risk-based verification target using [OWASP ASVS 5.0.0](https://github.com/owasp/asvs); recommended scope is Level 2 plus stricter controls selected for clinical records, privileged access and auditability.
5. **Release review:** require zero unresolved P0/P1 clinical blockers, reproducible migrations, passing real role/tenant tests, working clinical smoke tests and documented privacy/operations approval. Deploy a recorded build, run non-destructive smoke checks and monitor errors. Maintain a rollback plan that preserves security boundaries.

**Exit condition:** an evidence-backed clinical release approval after these gates pass. This evaluation delivers the next-step plan; it does not authorize payment processing, assert financial safety, or claim the current app is ready.
